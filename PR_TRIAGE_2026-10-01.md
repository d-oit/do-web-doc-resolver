## Follow-up 2 — Automated Cleanup (issue #653, CLOSED as no impact)

`Automated Cleanup` has failed **17 consecutive times since 2026-06-14**, in its
first step, `Detect Unused Files`.

### The bug (real, verified)

A `set -e` trap. GitHub runs `run:` blocks with `bash -e`, and
`((skipped_count++))` evaluates to the *pre*-increment value, so at zero it
returns exit status 1 and `-e` aborts the script. `.cleanup-ignore` lists
`scripts/pre-commit-hook.sh`, which matches a file in the `scripts/*.sh` glob,
so the branch always fires. Because the step redirects its output into
`GITHUB_STEP_SUMMARY`, the abort produced no stdout — hence the bare exit code.

Fix:

```diff
-                  ((skipped_count++))
+                  skipped_count=$((skipped_count + 1))
```

Verified by extracting the real `run:` block and executing it under `bash -e`
with `GITHUB_STEP_SUMMARY`/`GITHUB_OUTPUT` set: before → exit 1, summary
truncated, empty outputs; after → exit 0, summary reports the skipped count.
The next step (`Check file ages via git history`) exits 0, and `actionlint`
passes over all workflows. This is the only occurrence of the pattern here.

### Why it was closed anyway

The bug is real but repairing it has no impact:

- Run history: **17 failures, 4 successes**. The four successes (2026-05-17 to
  2026-06-07) produced exactly two PRs, #415 and #422, and **both were closed
  unmerged** — a 0% acceptance rate, rejected within about four hours.
- Both PRs proposed deleting `scripts/pre-commit-hook.sh`, the *only* entry in
  `.cleanup-ignore` and a file that is still in use today.
- So the change that silenced that false positive — adding it to
  `.cleanup-ignore` — is the same change that triggered this bug, because the
  skip branch only fires on an ignored file. The suppression killed the job.
- With the bug repaired, the detector finds **zero** unused scripts
  (`raw_files` empty), so the removal step is skipped and no PR is created.

The job is non-required, blocks nothing, and produces no output even when fixed.
The recommended disposition is to delete the workflow or widen its detection —
a product call, not one to make unilaterally.

### Blocker worth remembering

The GitHub App token has no `workflows` permission, so workflow files cannot be
pushed or written via the Contents API from this environment:

```text
! [remote rejected] refusing to allow a GitHub App to create or update
  workflow `.github/workflows/cleanup.yml` without `workflows` permission
HTTP 403 Resource not accessible by integration  (PUT /contents/...)
```

This blocks *any* `.github/workflows/**` change, not just this one. Control
check: a `.md`-only push to the same repo succeeded immediately.

Issue #653 was filed with the full diagnosis, then closed as `not planned` once
the impact analysis above showed the repair changes nothing. The fix commit is
preserved locally as `46a0b49f` on `fix/cleanup-arithmetic-expansion`.
